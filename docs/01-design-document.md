# SwimVault — 설계서 (Design Document)

> **한 줄 정의:** "큰 앱들이 볼 수 없는 우리 아이의, 모든 기록이 모이는 단 하나의 장소."
>
> 어느 대회·어느 리그·어느 나라든 결과지를 한 장 찍으면 → 우리 아이 기록만 추출 →
> 평생 기록부 + 진척·스플릿 분석. 기준은 USA Swimming 표든 우리 리그 자체 기준이든 적용.

문서 버전: v0.1 · 작성일: 2026-06-16 · 상태: 설계 + 골격(스캐폴딩)

---

## 1. 배경과 문제 정의

### 1.1 시장의 빈틈
기존 경쟁자(Swimmetry, Swim Track, SwimCloud)는 모두 **USA Swimming(USAS) 공인 선수 중심**이다.

| 제품 | 입력 방식 | 한계 |
|------|-----------|------|
| Swimmetry | USAS 데이터 자동 수집 | 데이터 의존 → 신뢰성 불안정("작동할 때만") |
| Swim Track | 수동 입력 | "Meet Mobile에서 import 해달라"는 수요 = 입력 고통 증명 |
| SwimCloud | USAS 중심 | 비공인 대회 선수는 아예 안 보임 |

→ **진짜 빈틈은 "분석"이 아니라 ① 입력 혁신 ② 방치된 세그먼트 ③ 흩어진 기록의 통합.**

### 1.2 타깃 (방치된 세그먼트)
여름 리그 · 동네 클럽 · YMCA · 고교 듀얼미트 · 마스터즈 · **해외(한국) 대회**에서만 뛰는 선수.
이들은 SWIMS(USAS 중앙 기록)에 없어 SwimCloud/Swimmetry에 **보이지 않고, 중앙 기록 자체가 없다.**

### 1.3 차별점 (해자)
1. **입력 혁신** — 아무 결과지나 사진/PDF/결과파일로.
2. **방치된 세그먼트** — 큰 앱이 못 보는 선수 전용.
3. **흩어진 기록 통합** — 특히 **한·미 양국에서 뛴 한인 아이의 두 시스템 기록 통합**(세상에 없는 도구 = 초기 커뮤니티 진입 훅).

## 2. 제품 원칙 (설계 제약)

| # | 원칙 | 설계에 미치는 영향 |
|---|------|--------------------|
| P1 | **데이터 파이프라인 0, 부모가 데이터 지참** | 스크래핑/외부 API 의존 없음. 업로드 중심. |
| P2 | **추출은 반드시 사람이 검증** | 0.01초가 의미. `1↔7, 0↔8, 콜론↔점` 오인 치명적. → "추출 결과 확인·수정" 단계 **필수**. |
| P3 | **사진 / PDF / 결과파일 3단 신뢰 계층** | 구조화 파일이 정확 → 신뢰도 점수로 구분. |
| P4 | **리텐션은 종단(longitudinal)에서** | "이번 한 번"이 아니라 "계속 쌓이는 기록부"로 설계. |
| P5 | **rec/여름엔 보편 기준 없음** | 진척·PB·스플릿·향상% 가 핵심 가치. 리그별 커스텀 기준 지원. |
| P6 | **미성년자 프라이버시** | 업로더 **본인 아이 중심**. 다른 아이 데이터로 검색 가능한 DB는 만들지 않음. |
| P7 | **"AI 분석"을 앞세우지 않음** | 입력 + 방치 세그먼트 + 통합을 앞세움. AI는 입력 도구일 뿐. |

## 3. 마이크로서비스 아키텍처

### 3.1 왜 마이크로서비스인가 (이 프로젝트 맥락)
> 요구사항: *"마이크로서비스로 만들어서 각각 요청 시 AI 토큰을 적게 사용하면서 바이브 코딩이 가능하도록."*

핵심은 **"AI로 코드를 수정할 때, 작은 서비스 하나의 컨텍스트만 로드하면 되도록"** 경계를 잘게 나누는 것.

**바이브 코딩 토큰 절약을 위한 설계 규칙:**
- **R1** — 한 서비스 = 한 책임. 서비스 디렉터리 하나만 읽으면 전체 맥락 파악 가능.
- **R2** — 각 서비스에 `CLAUDE.md`(또는 `AGENTS.md`)를 두어 그 서비스만의 컨텍스트를 요약 → AI가 저장소 전체를 읽지 않아도 됨.
- **R3** — 서비스 간 통신은 **`libs/contracts`의 타입/스키마**로만. 계약 파일만 공유 컨텍스트.
- **R4** — 파일은 작고 단일 목적(평균 < 150 LOC). 큰 파일은 토큰 비용 + 수정 충돌.
- **R5** — **AI(LLM) 호출은 `extraction-service`에 격리**. 런타임 AI 토큰 비용이 한 곳에만 발생 → 캐싱·배치·모델 선택을 한 곳에서 통제.

### 3.2 서비스 맵

                         │   frontend   │  React + Vite + TS

                                │ HTTPS / REST
                         ┌──────▼───────┐
                         │ api-gateway  │  Node/TS — 라우팅·인증검증·레이트리밋
                         └──────┬───────┘
       ┌──────────────┬────────┼────────┬───────────────┬──────────────┐
       ▼              ▼        ▼        ▼               ▼              ▼
┌────────────┐ ┌───────────┐ ┌──────────┐ ┌──────────────┐ ┌───────────┐ ┌────────────┐
│auth-service│ │  athlete  │ │ingestion │ │  extraction  │ │  records  │ │ standards  │
│  Node/TS   │ │  service  │ │ service  │ │   service    │ │  service  │ │  service   │
│  부모 계정  │ │  Node/TS  │ │ Node/TS  │ │ Python/FastAPI│ │  Node/TS  │ │  Node/TS   │
│  JWT       │ │ 아이 프로필 │ │업로드·저장 │ │ 비전+LLM 추출 │ │기록·스플릿 │ │USAS/커스텀 │
└────────────┘ └───────────┘ └────┬─────┘ └──────┬───────┘ │   ·PB     │ │   기준     │

                                                            │  service   │
                                                            │  Node/TS   │

                                                            │  스플릿분석 │

### 3.3 서비스별 책임

| 서비스 | 스택 | 책임 | AI 토큰 사용 |
|--------|------|------|--------------|
| `api-gateway` | Node/TS | 라우팅, JWT 검증, 레이트리밋, CORS | 없음 |
| `auth-service` | Node/TS | 부모 가입/로그인, JWT 발급, 비밀번호 해시 | 없음 |
| `athlete-service` | Node/TS | 아이(선수) 프로필 CRUD, 소속 리그/팀 | 없음 |
| `ingestion-service` | Node/TS | 파일 업로드(사진/PDF/.hy3/CL2), 저장, 추출 잡 생성 | 없음 |
| `extraction-service` | **Python/FastAPI** | **비전+LLM으로 결과지에서 우리 아이 기록만 추출**, 신뢰도 점수 | **여기에만 집중** |
| `records-service` | Node/TS | 확정된 기록 적재, 종목/거리/코스, 스플릿, PB 계산 | 없음 |
| `standards-service` | Node/TS | USAS 표준표(공개) + 리그별 커스텀 기준, 기준 대비 비교 | 없음 |
| `analytics-service` | Node/TS | 진척 그래프, 향상%, 스플릿 분석, 시즌/커리어 집계 | 없음 |

### 3.4 데이터 저장 (서비스별 DB 분리 원칙)
- 골격 단계: 각 서비스는 자체 스토리지 어댑터 인터페이스(`Repository`)를 가지며, 기본 구현은 인메모리 + (선택)PostgreSQL/SQLite.
- 운영 단계: 서비스별 스키마 분리(PostgreSQL schema-per-service) 또는 DB-per-service.
- 파일(원본 결과지)은 객체 스토리지(S3 호환) — 골격에서는 로컬 디스크 어댑터.

## 4. 핵심 플로우 — "사진 한 장 → 검증된 기록"

```
1. 부모: 결과지 사진/PDF/파일 업로드            [frontend → api-gateway → ingestion]
2. ingestion: 파일 저장, source_type 판별,        [ingestion]
   extraction job 생성 (사진=low / PDF=mid / 파일=high 신뢰계층)
3. extraction: 비전+LLM으로 "우리 아이" 기록만 추출 [extraction-service, ★유일한 AI 호출]
   → {종목, 거리, 코스, 최종기록, 스플릿[], 등수, confidence[]}
4. frontend: ★확인·수정 화면 (P2)                 [frontend]
   - 추출값 + confidence 색상 표시, 낮은 신뢰 필드 강조
   - 부모가 수정/확정
5. records: 확정 기록 적재, PB 갱신 판정           [records-service]
6. analytics/standards: 진척·향상%·기준 비교 갱신   [analytics, standards]
```

**신뢰 계층(P3) → confidence 기본값:**
| source_type | 기본 신뢰 | 추출 방식 |
|-------------|-----------|-----------|
| `result_file` (.hy3/.cl2/.sd3) | high | 구조화 파싱 (LLM 거의 불필요) |
| `pdf` | mid | 텍스트 레이어 파싱 + LLM 보정 |
| `photo` | low | 비전 모델 OCR + LLM 구조화 → **반드시 검증** |

## 5. 도메인 모델 (요약)

- **Parent** (계정) ──< owns >── **Athlete** (우리 아이)
- **Athlete** ──< has many >── **RaceResult** (대회 1종목 결과)
- **RaceResult** ──< has many >── **Split** (구간 기록)
- **RaceResult** belongs to **Meet** (대회: 이름, 날짜, 리그, 국가, 코스)
- **Standard** (기준): USAS 표준 또는 리그 커스텀 — (성별, 나이, 종목, 거리, 코스, 시간)
- **ExtractionJob**: 업로드 → 추출 → 검증 상태 추적

상세 스키마는 `docs/04-data-model.md`, 타입은 `libs/contracts`.

## 6. 기술 스택

| 영역 | 선택 | 이유 |
|------|------|------|
| 프론트엔드 | React + Vite + TypeScript | 빠른 DX, 모바일 PWA, 타입 공유 |
| Node 서비스 | TypeScript + Express + Zod | 언어 통일(토큰 절약), 런타임 검증 |
| 추출 서비스 | Python + FastAPI + Pydantic | 비전/LLM SDK 친화, 데이터 처리 강점 |
| 계약 공유 | `libs/contracts` (TS 타입 + JSON Schema) | 서비스 간 단일 진실 공급원 |
| LLM | Anthropic Claude (vision) | 결과지 OCR + 구조화. **extraction-service에만** |
| 테스트 | Jest(Node), Pytest(Py), Vitest(FE) | 표준·경량 |
| 로컬 오케스트레이션 | docker-compose | 1커맨드 기동 |

## 7. SW 품질 전략 (요약)

- **테스트 피라미드:** 단위(많이) → 통합(서비스 경계) → E2E(핵심 플로우 1개).
- **핵심 로직 우선 테스트:** ① PB 판정 ② 향상% 계산 ③ 시간 파싱/정규화(`1:02.34` ↔ `62.34s`) ④ 추출값 검증 규칙(P2) ⑤ 기준 대비 비교.
- **계약 테스트:** `libs/contracts` 스키마로 서비스 간 입출력 검증.
- **CI:** lint + typecheck + unit test (서비스별 병렬). 상세는 `docs/05-test-strategy.md`.

## 8. MVP 범위 / 비범위

**MVP 포함:** 업로드(3계층) → 추출(검증 UX) → 기록부 적재 → 진척/PB/스플릿 → USAS 공개 기준 + 리그 커스텀 기준 → 한·미 통합 뷰.

**비범위(의도적 제외):** 다른 아이 검색 가능한 종합 DB(P6), 자동 스크래핑(P1), 실시간 대회 중계, 소셜 피드.
